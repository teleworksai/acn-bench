# ADR-26 — T06b2: tool choice for compaction and forked children

**Status:** accepted (T06b2; Class B: `acn-harness`, `acn-mockllm`). **IDs affected:** HAR-4, HAR-14, HAR-21, HAR-60; MLM-1, MLM-10, MLM-40; P4-12.

## Context
SPEC 040 v0.2 and SPEC 030 v0.2 (PR #28) settle issues #24 and #25:
- the compaction call forbids tool calls;
- a forked child presents the parent's tools but calls only its own;
- the mock honours both.

Implementing them needs these readings.

## Decision
- **The tool choice is part of the context.** `Context` carries `tool_choice: Option<ToolChoice>`: `Forbid`, or `Allowed(names)` in the child specification's order (HAR-21's "a function of the context").
  - `Context::encode` takes a sixth argument, `subset`, for backends that accept an allowed-tools restriction.
  - `Backend::restricts_tools` is true for `mockllm` and `openai` only.
  - A context with no tools never carries a tool choice.
  - `Allowed` on the messages dialect, or on `vllm` and `sglang`, writes nothing: the instruction line carries the restriction (HAR-14).
- **Compaction** sets `Forbid` on the compaction call's copy of the context when it has tools. The tools themselves are unchanged, so the prefix is the context's (HAR-4).
- **Forked children.**
  - **The lineage.** A forked child's lineage keeps `tools`, the parent's, which it presents. A new field, `allowed`, holds the child specification's tools, which it executes; `run_tool` checks `allowed` when it is set. A call outside the set gets the unknown-tool error result, so the child's turn goes on as it would after any refused call.
  - **The first request** gets the instruction line after `(child i of w)` and one `\n`: `Use only these tools: a, b.`, or `Use no tools.` when the specification lists none. Every request of the child carries `Allowed` (or `Forbid` when empty).
- **HAR-60's new refusal** applies to every task that lists a `subagent` tool: each of the child's tools must be among that task's tools. A task that does not list the `subagent` tool is not constrained.
- **The mock (MLM-40).**
  - **`allowed_tools` names** are read from each entry's `function.name`, kept in the list's order, and dropped when not among `tools`. The tool called is the one at (results since the last user message) modulo the count; with none left, the reply is text.
  - **`none`**, in either form, gives text.
  - **Every other `tool_choice`** (`auto`, `required`, a named function) leaves the policy as before.
  - **`tool_choice` is not read by `prompt::prompt`**, so the prompt bytes and the cache accounting are unchanged (MLM-10).
- **Issue #26, the tool-order confound, is recorded, not fixed.** Making MLM-40's unrestricted choice independent of presentation order would change which tool the mock calls on every workload and test. SPEC 100 P4-12(c) accepts a stated confound instead, so the run of record states it with the `tool_order_stable` effect.

## Consequences
- On the mock, compaction summaries are text, and forked children do their own tool work.
- The `compaction_trigger` and `fanout_prompting` effects of POC 4 on the mock now measure caching. Two differences from the providers remain, and SPEC 100 P4-12 requires stating them: Anthropic may invalidate message blocks on a change of tool choice, and the restriction rests on the model's instruction off `openai`.
- Sim bundles of runs that compact or fork change bytes: the mock's text replies draw from its RNG. Anything that pinned such bytes is regenerated by the tests that own it.
