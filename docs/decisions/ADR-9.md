# ADR-9 — Solo-maintainer mode for review (CON-16)

**Status:** accepted (owner decision, 2026-09-18; wording tightened by the pre-landing review). **IDs affected:** CON-10, CON-16.

## Context
CON-16 required every PR to be implemented and reviewed by different agents or people. The project currently has one maintainer. In practice that meant every merge was an admin override of a one-approval rule, with an agent session standing in for the second person: ceremony that cannot add a second human judgement, and a habit of overriding protection that is worse than not having the rule.

## Decision
- **The mode is read from the base branch.** The project is in solo-maintainer mode while `.github/CODEOWNERS` on a PR's base branch names exactly one `@user` handle across all its entries. Everything else (no file, no entries, an ownerless or malformed entry, an org team, an e-mail address, a second handle) is not solo mode, and a PR that changes the owners is handled under the stricter of its base and its head. A PR therefore cannot remove the second owner to exempt itself, and an empty file does not mean "no review needed".
- **In solo mode** independent review is not a merge condition. The maintainer merges once the CON-9 gates and the required CI checks ADR-6 names, `pr-check` included, are green on the head commit. A review by a separate agent session should be requested for Class C changes (the adversarial prompt) and for Class B changes the maintainer judges risky (the cross-review prompt). A change to an already recorded hypothesis or measured trace that merges without one says so in its description.
- **Who merges.** The maintainer is the human owner. An agent session runs with the maintainer's credentials, so GitHub cannot tell the two apart; the rule can. An agent never merges on its own initiative and may run a merge only on the maintainer's instruction naming that PR. That is also what "human-merged" means in CON-7, CON-22 and LOOP-20: the human decided that merge.
- **With a second owner** every PR needs an approving GitHub review from a person other than its author. An agent cross-review informs that approval and never replaces it, in either mode. The earlier rule let one person's two agent sessions satisfy it, which is the ceremony this ADR set out to remove.
- **The switch back needs no spec change, and nothing performs it for you.** Adding a second owner to CODEOWNERS changes the mode. The same step has to raise the branch-protection approval count to 1 and require code-owner review, which are repository settings.
- **What does not relax:** the gates, the `spec-change` and `env-change` label rules, the human merge of CON-7 and CON-22, and, after the M0 gate, the adversarial review of CON-7. With one maintainer that review is a separate agent session running the adversarial prompt, linked from the PR. This settles the question the first version of this ADR left open; the owner can choose otherwise before M0 closes.

## What solo mode leaves to the author
Review caught what the gates missed on the bootstrap PRs, so it is worth saying what nothing checks now. Machine-checked, while the checks are required: formatting and lints (CON-5b, CON-19), layout and CLI shape (CON-6, CON-8), that a citation exists (CON-12), that the environment record was updated (CON-7), banned dependencies (CON-20), and labels (CON-14; CON-7 after M0). Left to the author's diligence: whether a citing test really exercises its MUST; stopping on a spec conflict (CON-13); the rationale and IDs of a spec change (CON-14); ADRs for interpretations (CON-15); the class declaration and that Class B acceptance suites ran (CON-10); one concern per PR (CON-11); freezing before the first cited run (CON-17, HYP-26); that a control is present (CON-18); no payload in measured traces (CON-21); every frozen-set change before M0, while `env-change` is advisory; and a PR that rewrites its own checker (ADR-6, amendment 2). SPEC 080 §6 question 10 names the same dependency for freeze reviews.

## Consequences
Agent reviews stay useful and cheap to request: on the foundation PRs they found real gate bypasses and spec holes. They are a tool the maintainer reaches for, with a stated default for Class C. The repository settings must match: `pr-check`, `lab` and the arm64 gate as required checks, and `enforce_admins` on, as GETTING-STARTED describes; at the time of writing the live settings require two checks and leave admin enforcement off.
