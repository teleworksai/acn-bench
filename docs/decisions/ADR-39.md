# ADR-39 — T14: a local control plane that starts runs and decides nothing

**Status:** accepted (T14.1; `spec-change`, SPEC 070 Draft v0.1). **IDs affected:** CTL-1 to CTL-30; CON-5, CON-8, CON-27, CON-28, CON-29; TRC-23, TRC-42; HAR-22, HAR-23, HAR-25, HAR-26, HAR-50; GEN-22; LOOP-12, LOOP-20; EMU-10, EMU-20, EMU-49.

## Context
SPEC 070 was "to write". T14 asks for an axum HTTP/JSON API to create scenarios, start runs, poll status and fetch bundles. It also asks for a run registry on disk, endpoints for external inference nodes and partner endpoints, and an OpenAPI document generated by `docs-inventory`. LOOP-20 makes `acn ctl` one of the two ways an agent may drive the loop.

## Decision
- **The control plane starts runs and decides nothing.** A run started through it is a CLI run of SPEC 040 or SPEC 050, with the same identity and the same bundle. The acceptance test compares the two.
- **Loopback only, no authentication (CTL-1).** v0.1 is a local service for one person or an agent on the same machine. Serving beyond loopback needs a threat model; until then, an SSH tunnel reaches it.
- **Origin checks (CTL-3).** Loopback alone does not stop a web page in a local browser from rebinding a name to 127.0.0.1, or from posting a plain form. So every request must carry a loopback `Host`, and every write a JSON or TOML content type, which a plain form cannot send. Ids are checked as hex before they touch a path.
- **One JSON object when it stops.** `acn ctl serve` is the first long-running command. It keeps CON-8 by printing its object on shutdown, with the `run_ids` it started or adopted, and logging its address on stderr. It fails only when it cannot bind or cannot finish cleanly. ADR-36 declined a standalone `acn proxy` for exactly this reason; here a server is the point of the task.
- **A registry of requests named by their resolved inputs (CTL-11, CTL-13).**
  - A request's id hashes the request together with every input file's BLAKE3 and its endpoint's URL, under a context string with a known-answer vector (CON-27). An edit to a workload, sheet or hypothesis is therefore a new request. The first draft hashed paths alone, so an edited input would have returned the old run (the review caught it). An input that changes after submission fails the run with `input_changed`.
  - Submitting is idempotent. A request survives a restart: an interrupted one is marked, and queued ones are queued again in submission order.
  - A failed request reruns only when asked, so a retry is a decision someone made.
  - The worker computes the run's id before running. If the bundle already exists, it is verified and adopted (`reused`), whoever made it. Two requests that CON-29 makes one run are one bundle. A `live` measurement is therefore never repeated in the same runs directory, as with LOOP-12's twins.
- **One worker, in submission order (CTL-12).** Two `live` runs never share the clock or the loopback ports, and nothing depends on scheduling. Parallel `sim` runs are a later question.
- **Scenarios.** A stored scenario sits in a directory named by its hash, under its own name (EMU-20). A trace-driven scenario reads files beside it (EMU-10), so it cannot be stored and is named by its workspace path, as the CLI names it.
- **Typed requests.** A seed is a decimal string, because JSON numbers lose precision above 2^53. `vary` values are text, typed as the CLI types them. Options are those with CLI flags, absent ones at their default; `opt.keep_content` cannot be set, so no bundle made through the server carries content.
- **Paths inside the workspace (CTL-10).** Every path a request names resolves inside the workspace root, and a run writes only its bundle under `runs/`. That is LOOP-20's rule for anything an agent can drive. Loop commands through the API, which write reports and verdicts, are a later version.
- **Named endpoints without credentials (CTL-30).** An endpoint is a backend and a URL. Credentials stay in the server's environment, as HAR-22 has them for the CLI.
- **Bundles served by their manifest (CTL-22, CTL-23).** Only files the manifest lists are served, each after a hash check, so the API never exposes another file under `runs/`.
- **OpenAPI from the route table (CTL-24).** axum makes no OpenAPI, so one hand-written route table builds both the router and the document, and they cannot drift.
  - The document is committed as JSON, and an `acn-ctl` test keeps it equal to the table's.
  - `docs-inventory` renders the page from that file alone. `xtask`, which CODEOWNERS protects, therefore gains no dependency on the server's crates.

## Consequences
- T14 is planned as:
  - T14.1, this `spec-change`;
  - T14.2, `acn-ctl`'s registry, worker and API, with `acn ctl serve`;
  - T14.3, the OpenAPI page in `docs-inventory` and the acceptance suite.

  All are Class B. T14.2 adds to `acn-harness` and `acn-gen` a way to compute a run's id before running it, from the same code that names the bundle.
- `acn-ctl` depends on `acn-harness`, `acn-gen` and `acn-emu`, as PLAN.md's dependency line says (`acn-ctl` ← all runtime crates).
- M3's runs against real inference nodes reach them as named endpoints, with no further change to this API.

## T14.2 notes
- **T14.2 is two PRs.**
  - T14.2a: the pre-run identity, and `acn-ctl`'s requests, resolution, registry and worker, with no HTTP.
  - T14.2b: the API, its route table and OpenAPI file, endpoints, scenarios, bundles and `acn ctl serve`.
- **A run's identity before it runs.**
  - `Bundle::plan` makes the checked manifest, `run_id` included, without writing anything; `Bundle::create` is `plan` then `create`.
  - The harness's `run_driven` does everything before the network and the runs directory in one `prepare`, shared by `plan_driven`, so a plan's `run_id` is the run's (tested in every mode). The generator's `plan_run` shares its `prepare` with `run` the same way, including the rewrite of an empty live endpoint to the served mock, which is part of the identity.
  - A plan does not probe the endpoint (HAR-23). The run still does, before its bundle exists.
- **`request_id`.**
  - It is the BLAKE3 of `acn-bench/ctl_request/v1\0` and `request.json`'s exact bytes, trailing newline included, so anyone can check an id against its file. Its known-answer vector is in `crates/acn-ctl/tests/registry.rs`.
  - The resolved request has three keys: `request` (paths normalised to the workspace root, absent options absent, `retry` left out), `hashes`, and `endpoint_url` when a name was resolved.
  - The canonical JSON is rendered by `acn-ctl`'s own key-sorting writer. A float, the only one being `stall_threshold_ms`, uses `serde_json`'s shortest round-trip text.
- **Status details.**
  - A `running` status carries its `run_id`, so that a restart can find its bundle.
  - On restart, a bundle that verifies is kept (a crash after it was finished, before its status was written), so a retry adopts it. One that does not verify is removed.
  - A retry gets a new `seq`.
  - Submission checks only what needs no run (CTL-21): paths, fields, scenario and endpoint names. A plan or preflight refusal shows as a `failed` status with a code from the harness's error.
- **Paths.**
  - A path resolves inside the root after following links. A link inside the workspace to a file inside it is allowed, and one out of it is refused.
  - `--runs-dir` may not be absolute, contain `..`, or lie in a protected path.
- **The trace scope.**
  - `trace-scope.toml` now lists SPEC 050's GEN ids and SPEC 070's CTL-10 to CTL-13.
  - It also lists the ids already implemented by T11b and T13 that it had missed: LOOP-12, LOOP-16 and HAR-26.
  - All were already cited by tests; trace-check had not required them.
- **After review (PR 57).**
  - **One run at a time, whoever calls.** An execution lock is held across every run, so two workers, or a worker and `run_next`, never overlap. `stop()` takes the queue's lock, so a worker about to wait cannot miss it.
  - **Retries.** A retry is queued under the registry's lock, so two concurrent retries queue it once.
  - **Request files.** On opening, a request whose `request.json` is missing or is not its id's bytes is dropped when it has no status, and failed with `internal` when it has one. A resubmission rewrites a partial file. A request that cannot be read when its turn comes fails instead of staying queued.
  - **The plan's inputs.** The planned workload, hypothesis and scenario hashes must be the resolved ones, and a stored scenario's file must still have its hash; otherwise `input_changed`. A run that makes another `run_id` than planned is an internal fault. A refusal that is not an existing directory is reported as itself.
  - **A crashed run.** A run that panicked did not clean up after itself (HAR-23). Its unfinished bundle is removed, so a retry can run.
  - **The runs directory.** It is checked after canonicalizing, so neither a link nor a `.` hides a protected path. The comparison ignores case, for case-insensitive file systems. An empty path is refused.
  - **One writer.** The control plane assumes it is the only process writing its runs directory while it runs. A restart removes an unfinished bundle at a `running` request's run_id, which would also remove a CLI run in progress there. Run the CLI into another runs directory, or stop the server first.
  - **Canonical values.** A seed has no leading zero, and a stall threshold is not negative; −0 is written 0 (CON-27(c)). The known-answer vector carries the one float, as CON-27(d) asks.
  - **Adopting another build's bundle** is a reuse, not a mismatch: the build is not part of `run_id` (CON-31), and HYP-20 still refuses a set that mixes builds within one mode.
  - An identity error from a request's input maps to `config`.
- **T14.2b, the API.**
  - **One table builds the router.** Its handlers are the table's routes, each dispatched by operation, with the content-type check before any work. Unknown paths answer the JSON fallback, so every answer is one object.
  - **The answers that are not `{ok, ...}`.** A bundle file's bytes (CTL-23), and the OpenAPI document itself (CTL-24). A top-level `ok` would make the document invalid OpenAPI.
  - **The committed document.** `crates/acn-ctl/openapi.json`: pretty, sorted JSON with one newline. A test keeps it equal to the table's; `ACN_WRITE_OPENAPI=1` rewrites it. The response schemas name one common `Answer` object (`ok`, `code`, `error`), and the request schemas give each body's media type.
  - **Status codes.** `bundle_invalid` is 409; an unknown scenario, endpoint, request or bundle is 404. A request missing `Host` gets hyper's own 400 or the guard's 421.
  - **Handlers run off the runtime.** The registry's file work runs on `spawn_blocking`.
  - **Bodies are capped.** 1 MiB.
  - **Shutdown.** `POST /v1/shutdown` stops the registry, so later submissions get 503, and then the server. The worker finishes the run in progress before the summary is printed.
  - **Endpoints** are checked by the harness's own `--endpoint` check, `endpoint_url`, now public, so a registered URL is one a CLI run accepts. `acn-mock://loopback` is accepted for `mockllm` only. An endpoint is written by temporary file and rename.
  - **Scenarios** are written to a staging directory and loaded there by `acn_emu::scenario::load`, so the name-is-stem rule (EMU-20) applies, then renamed into place.
  - **`acn ctl serve`** runs only inside a workspace, resolving `--runs-dir` against its root as `loop run` does.
  - **Credentials.** The credential test runs the server in a child process with a key in its environment, because `set_var` is `unsafe`.
- **After review (PR 58).**
  - **Bind first.** `acn ctl serve` binds its port before it opens the registry, so a server that cannot bind recovers nothing. The registry also takes an exclusive lock on `<runs>/ctl/lock` (`File::try_lock`) before reading anything, and a second one on the same runs directory is refused with 409 `registry_in_use`. The OS releases the lock when the process dies. `Server::bind_with` binds a registry already open, for tests that set its hooks.
  - **axum's own refusals are JSON.** A method a path does not take answers 405 `method_not_allowed`, a body over 1 MiB answers 413 `payload_too_large`, and a path or body axum cannot read answers 400. The route test requires a JSON object from every route except a bundle file's.
  - **While stopping**, from the signal on, every write but `shutdown` answers 503 `shutting_down`; reads are served while connections drain. Connections get 5 s to finish, then the server closes them and the worker finishes the run in progress.
  - **Endpoints and submissions share the registry's lock.** A submission holds it from resolution to queuing, and a delete checks for a queued or running request and removes the file under it, so a request never queues on an endpoint being deleted.
  - **Scenario staging.** Each store stages in its own numbered directory. A rename that fails is a success only when the scenario is already in place with the same name, and a 500 otherwise.
  - **Empty bodies.** `shutdown` and `DELETE /v1/endpoints/{name}` take an empty body or `{}`, and nothing else.
  - **The Host check** takes exactly one `Host` header, compared byte for byte (so `LOCALHOST:<port>` is refused; clients send lower case).
  - **The document.** Every route also lists 421 and 500; routes with a body list 413; writes list 503. The request bodies name `Submit`, `Endpoint` and `Empty` schemas. The 200 of `get_bundle_file` is binary, and that of `openapi` is the document. The file is checked out byte for byte (`-text`).
  - **The summary's `ok`** is false when the runtime cannot start, the worker cannot be spawned or panics, the server fails, or the registry records a fault. Its `run_ids` are the runs the registry finished or adopted, not the requests it queued.
  - **A handler that panics** answers a fixed `internal` message and logs the cause, so the answer never carries a panic's text.
  - **`real-api`.** `acn-ctl` has the feature, which `acn-cli`'s enables. The credential test asserts that a live OpenAI request is accepted and fails, with or without it, and that neither the answers nor the child's log (now with a subscriber) carry the key.
- **T14.3, the API page and the acceptance suite.**
  - **The page.** `cargo xtask docs-inventory` renders `crates/acn-ctl/openapi.json` as `docs/generated/ctl-api.md`: a route table (method, path, operation, summary, body, statuses), each route's responses, and the component schemas, with nested fields and the forms of a `oneOf` flattened under dotted names and each field's pattern, minimum and description. It reads only the JSON, through `serde_json`, which `xtask` already had. A root without the document has no page; a document without `paths`, or with a method the page does not render, fails the task.
  - **The document describes the answers.** Each route's success answer has its own schema (`Submitted`, `Run` with `Status`, `Runs`, `Bundle`, `Scenario`, `Stored`, `Endpoints`, `Named`, `Ok`), every refusal is `Refusal`, and a bundle file is typed by its extension (Parquet, JSON or bytes). The API tests check that each real answer carries its schema's required fields. The `Submit` schema carries what validation enforces as enums and patterns (`mode`, `arm`, `backend`, the seed's bound, `scenario.hash`), and the cross-field rules (which fields each `kind` names, one of `hypothesis` and `seed`, one of `endpoint` and `endpoint_name`) as text.
  - **The documented request is the parsed one.** An `acn-ctl` test builds a `Submit` with every field set, as an exhaustive struct literal, so a field added to the parser fails to compile there until it is documented. The test then compares the serialized fields, and `ReqOpts`', with the schema's, checks the required set against the parser, and checks that the documented enums are the values validation takes.
  - **Bodies.** A write route's body is documented as required, since the content type is (CTL-3); `Empty` says an empty body is taken as `{}`. `shutdown` lists 400 (a body other than `{}`) and not 503, since a repeated shutdown is served while stopping.
  - **Logs.** The server logs `acn ctl stopping` when it begins to stop, and the worker `acn ctl run done` or `acn ctl run failed` when a run ends.
  - **Where the suite lives.** `tests/accept/ctl.rs` drives the `acn` binary, and only `acn-cli`'s own tests can name it (`CARGO_BIN_EXE_acn`). So it is declared as `acn-cli`'s test `accept_ctl`, with its file under `tests/accept/` as SPEC 070 §5 says, and `tests/accept/Cargo.toml` points to it. Run it with `cargo test -p acn-cli --test accept_ctl`; `cargo test --workspace` runs it.
  - **Its workspace is this checkout.** The binary refuses a root whose frozen code is not the code it was built from (CON-31), so the suite works in a scratch directory under `<root>/target/accept-ctl/`, inside the root whatever `CARGO_TARGET_DIR` is, and removed when the test ends (one left by a killed test is ignored by git). The CLI writes into that directory's `cli-runs`, and the server into its `runs`, named relative to the root as `--runs-dir` must be.
  - **What it checks.**
    - Three runs have the same `run_id` and bundle digest from the CLI and through the server, and the server's are not adopted: a default harness run, a generator run, and a harness run with `arm`, `replicates`, a knob `vary`, run options and a scenario set, the scenario stored and named by its hash on the server's side.
    - Stopped by SIGTERM and, in a second test, by `POST /v1/shutdown`, while a live run on the served mock is `running`, the server exits 0 and prints one object with its own address, at least the requests the test made, and `run_ids` naming that run. The log shows the run ended after the server began to stop, and its bundle verifies.
    - The server logs a `127.0.0.1` address; on Linux, another loopback address is not served, so it is a specific bind. A server that cannot bind prints `ok: false` and exits 1 (`crates/acn-cli/tests/cli_contract.rs`).
    - A server process is killed if its test fails, and a server that does not stop fails its test after two minutes.
