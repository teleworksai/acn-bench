# ADR-6 — `cargo xtask pr-check`: label rules and CODEOWNERS coverage as machine checks

**Status:** accepted (xtask hardening). **IDs affected:** CON-7, CON-14, LOOP-20.

## Context
CON-14 (spec edits need the `spec-change` label), CON-7 (frozen-set edits need `env-change`) and LOOP-20 (CI verifies that CODEOWNERS covers the protected paths) were rules on paper: no check failed when they were broken. The constitution also says the `env-change` procedure applies "after the M0 gate", while T02–T05 legitimately populate frozen directories before it.

## Decision
- `cargo xtask pr-check [--base <ref> | --changed a,b,…] [--labels x,y]` prints one CON-8 object. With a change list it fails when a path under `specs/` changed without the `spec-change` label, and when a frozen-set path or `env-hash.json` changed without `env-change`.
- The `env-change` rule is enforced only once `docs/gates/M0.md` exists. In git mode the record is looked up on the merge base as well as on the head, so a PR cannot reopen the frozen set by deleting the gate record in the same change. Before that the same finding is returned under `advisories` and does not fail, so bootstrap tasks are not blocked and nobody learns to apply the label reflexively.
- With or without a change list, the task fails unless `.github/CODEOWNERS` protects each frozen path, `/specs/`, `/env-hash.json`, `/trace-scope.toml`, `/docs/gates/` and `/.github/CODEOWNERS` itself. GitHub applies the **last** matching pattern, so a path counts as protected only when the last entry that could match it (a catch-all, a parent, a child glob or the path itself) is the exact path with a real owner (`@user`, `@org/team` or an e-mail). Globs and parent directories never count as coverage, and the overlap test over-approximates gitignore matching on purpose: an unanchored pattern (`mod.rs`, `core/`, `*.md`) can match at any depth and so overlaps every protected path, and an anchored glob overlaps whenever its literal prefix and the protected path share a string prefix (`/spec*`). The check fails closed; keep the exact protected entries last in the file.
- Changed paths come from `git diff --no-renames --name-only -z`, so both sides of a move are seen and non-ASCII paths are not quoted; explicit paths are normalised lexically (`./`, `..`) and matched case-insensitively, because the primary platform's filesystem is. A `--base` beginning with `-` is refused. The list is derived from the same `FROZEN_SET` constant that `env-hash` uses, so the two cannot drift.
- The CON-9 gate chain is fixed by the constitution and is not extended. The static half runs inside `cargo test` through a self-hosting test; the label half needs the PR's labels and base ref, so it runs as its own CI job, which the CI PR of the same series adds (`.github/workflows/pr-check.yml`). Until that job is on `main` and is a required check, the label rules are implemented but not enforced.

## Consequences
A mislabelled PR fails a required check instead of relying on reviewer memory. The check is advisory about who merges: GitHub branch protection still has to require code-owner review for CODEOWNERS to bind, which is a repository setting, not code.

## Amendment (pre-landing review) — resolved commits, and a matcher that fails closed
An adversarial review reproduced several ways to make `pr-check` pass while a rule was broken. The tool now works as follows.
- **Commits, not names.** `--base` is resolved once to a commit and everything afterwards uses SHAs. A short name that exists in more than one of `refs/tags`, `refs/heads` and `refs/remotes` is refused, because git prefers tags and a pushed tag named `origin/main` would silently replace the base branch; pass a full ref name or a SHA. An unresolvable base, unrelated histories, and a `--root` that is not the repository top level are errors. The report carries `base_sha`, `merge_base`, `head_sha` and `changed_paths`, so an empty diff cannot pass for a docs-only PR unseen.
- **Gate state.** M0 counts as closed if the record exists on the merge base, on the tip of the base, on the head, or in the working tree: a branch forked before the gate closed must not see it open. Lookups use `git ls-tree`; a failing lookup is an error, never "absent".
- **Gate records.** Changing or deleting an existing file under `docs/gates/` is a frozen-set change. This closes the two-step reopen (delete `M0.md` in one PR, edit the frozen set in the next). Adding a new gate record needs no label. In `--changed` mode there is no history, so any listed gate record is treated as existing and a listed `M0.md` as proof that the gate is closed.
- **Scope file.** Removing an ID or a section from `trace-scope.toml`, or deleting the file, needs the `spec-change` label: it stops a requirement's tests from being required. Additions are free.
- **Paths.** Git paths are used as git prints them (`--no-renames`, `-z`, `--ignore-submodules=none`, so a `.gitmodules` `ignore = all` cannot hide a gitlink). A path equal to a protected directory counts (a gitlink or symlink in its place). Matching uses full case folding, because `Specs/` and `ſpecs/` name `specs/` on the primary platform. A backslash is a file-name character and is left alone. In `--changed` mode an absolute path, or one that climbs out of the root, is an error.
- **CODEOWNERS.** A protected path counts as covered only when the last entry that could match it is byte-for-byte the canonical entry (`/specs/`, `/env-hash.json`) and every token after the pattern is a valid owner (`@user`, `@org/team`, an e-mail address). `//specs/` and `/env-hash.json/` are different gitignore patterns and do not count. For the overlap test, a negated or unanchored pattern overlaps everything, and backslash escapes are removed first. Only space and tab separate tokens. A file over GitHub's 3 MB limit is an error. Not checked, and left to the owner: whether the named owners exist and have write access.
- **Labels.** CI passes labels as a JSON array (`--labels-json`), so a label containing a comma cannot pose as two. `--labels` stays for local use.
- **Isolation.** Git is spawned with `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and their relatives removed from the environment. A hook or `rebase --exec` exports them, and they override `-C`; before this, running the test suite from a hook committed into the developer's real repository.
- **Not solved here.** The check is built from the PR under test, so a PR can edit `pr_check.rs` or the workflow. That needs CODEOWNERS entries for `crates/xtask/` and `.github/workflows/` (added in the CI PR) plus required code-owner review, which is a repository setting that solo-maintainer mode leaves off.

## Amendment 2 (pre-landing review of the CI PR) — enforcement points, live labels, workflows compared whole
Three reviewers broke the first version of the CI layer without touching a protected path. The changes below close what a repository file can close; the last bullet lists what only a repository setting can.
- **Enforcement points.** `pr_check::ENFORCEMENT_POINTS` names the files that decide what the gates check or how they run: `.github/workflows/`, `.github/dependabot.yml`, `.cargo/`, the root `Cargo.toml` and `Cargo.lock` (they choose the code the checker is built from), `clippy.toml`, `deny.toml`, `rust-toolchain.toml`, `tools/ci.sh`, `crates/xtask/` and `lab/clippy.toml`. `pr-check` fails unless CODEOWNERS carries the canonical entry for each, exactly as for the frozen set. No label rule is attached to them: a label is a statement of intent, and what these paths need is an owner's eyes.
- **Live labels and base.** The workflow reads the PR's labels and base branch from the API when the job runs. The event payload is a snapshot, and "Re-run jobs" replays it: label a PR, get a green run, remove the label, re-run the green run, and the newest `pr-check` result on the commit is green with no label. The job needs `pull-requests: read` for this and nothing more. Values reach the shell through the environment and a file, never through `${{ }}` inside the script.
- **Workflows compared whole.** `crates/xtask/tests/workspace.rs` parses both workflows as YAML and compares them with a copy held in the test, after checking that every `uses:` is an `owner/repo@<40 hex>` pin and masking the SHA (so Dependabot bumps pass). The earlier tests matched lines of text anywhere in the file; mutation testing moved `tools/ci.sh` into a job that never runs, wrote `"if": false`, added a matrix `exclude`, and replaced the nightly command with `echo`, all green. A change to a workflow is now made twice, the second time in a file CODEOWNERS covers. The test also fixes the set of workflow files at two, because a second workflow can report a check under a required name. Required jobs and their steps may not carry `if`, `continue-on-error`, `timeout-minutes`, `shell` or `working-directory`.
- **Supply chain.** `persist-credentials: false` on every checkout, so build scripts and tests of the PR never see the token. `cargo-deny` is pinned to a version with `fallback: none`, so it does not move with each bump of the install action and is only ever the checksum-verified release.
- **Not solved by files.** A `pull_request` workflow and the `xtask` it builds come from the PR itself, so a PR that rewrites both still judges itself. Closing that needs settings the owner controls: `pr-check`, `lab` and `gates (ubuntu-24.04-arm)` as required checks; required code-owner review once there is a second owner (CON-16 solo-maintainer mode leaves it off, and an author cannot approve their own PR); `enforce_admins`; and the Actions policy that requires SHA-pinned actions. A base-built check under `pull_request_target` would remove the self-judging, at the price of a workflow that must never check out or build head code; it is left for a separate decision.
