# ADR-4 — `env-hash` covers exactly the frozen set and is recorded at the root

**Status:** accepted (T01). **IDs affected:** CON-5(e), CON-7, CON-9.

## Context
CON-7 requires an `env-change` PR to carry "the updated output of `cargo xtask env-hash`" and CON-9 gates on `env-hash --check`, but neither says what the hash covers nor where the reference value lives. CON-5(e) later folds `env_hash` into `run_id`, so the definition must be stable and machine-readable.

## Decision
- **Coverage** is the frozen set as listed in CON-7, and nothing else: `hypotheses/`, `scenarios/measured/`, `crates/acn-hyp/`, `crates/acn-attrib/src/core/`, `crates/acn-trace/src/schema/`. Nothing is skipped by name except a zero-length `.gitkeep`: a placeholder with content is content (`#[path]` and `include!` can turn any file name into code), `.DS_Store` is refused with a message saying how to remove it, and symlinks and special files are refused because their targets would be hashed by name only. Files are hashed from the working tree as it is, so an editor swap file or a build directory inside a frozen directory changes the hash; keep frozen directories clean. The toolchain pin and `Cargo.lock` are deliberately not included; if reproducibility work later needs them in `run_id`, that is a separate, named input rather than a widening of the frozen-set hash.
- **Definition.** For each file, `blake3(contents)`; the environment hash is `blake3` over the sorted sequence of `path \0 file_hash \n` records, paths relative to the root with forward slashes. Platform-independent and order-independent of the filesystem.
- **Record.** `env-hash.json` at the workspace root holds the hash and the per-file list, written only by `cargo xtask env-hash --write`. It is added to CODEOWNERS next to the frozen paths so it cannot change without the Class C owner.

## Consequences
A change to any frozen file fails `env-hash --check` until the record is rewritten in the same PR, which is the mechanical hook for the `env-change` process. Adding a file to a frozen directory also moves the hash. Run-time consumers (`acn-cli`, T02+) read `env-hash.json` rather than recomputing, so a bundle's `env_hash` is the value that was reviewed.

## Amendment 1 — the build is hashed separately (CON-31)
The decision above keeps the toolchain pin and `Cargo.lock` out of `env_hash`. That left a hole: a bump of Arrow, Parquet, zstd or the compiler changes a bundle's bytes while `env_hash` and `run_id` stay the same, so the byte-identity claim of CON-5(c) was not backed by any recorded value. Constitution v0.2 answers it with `build_hash` (CON-31), carried in every manifest and deliberately not an input of `run_id`. It covers `Cargo.lock`, the toolchain pin, a tree hash of the workspace's own source under `crates/` (the lockfile records path members by name and version only, so without this an edit to a run-path crate would be invisible), the target triple, the profile and the feature set, and it is computed at compile time and embedded in the binary. It does not make bundles identical across target triples: platform maths libraries differ in the last bit, so identity is claimed only within one target. `env_hash` keeps its meaning: the frozen set that defines the *question*. `build_hash` names the *binary* that answered it.

## Amendment 2 — runs recompute; they do not trust the record
The Consequences above say run-time consumers read `env-hash.json` rather than recomputing. CON-28 supersedes that: a run finds the workspace root (the nearest ancestor holding `env-hash.json`), recomputes the hashes and refuses to start on a mismatch, so a bundle can never carry the reviewed value over a tree that has drifted from it. Outside a checkout, only runs with no hypothesis or a candidate hypothesis may start; a published kit ships the record and the frozen set.

## Amendment (pre-landing review of T01) — `--check` verifies the whole record
`--check` first compared only the top-level `env_hash`. A one-line edit to that value would pass while every per-file hash, which is what a reviewer reads to see which frozen file moved, still said nothing had changed. The check now requires the recorded `files` list to hash to the recorded `env_hash` and the whole record to equal the computed one. A missing frozen directory or a `--root` that is not a directory is an error, never an empty set, and `--write` does not read the old record, so it can repair a corrupt one.

## Amendment 3 — runs are bound to `engine_hash`, not to the whole set (CON-28, ADR-10)
`env_hash` covers every frozen hypothesis file. It was also an input of `run_id` and the value a verdict compared, so freezing a second POC's hypothesis would have changed the `run_id` of every cell of the first and made its bundles, including real-provider runs that cannot be regenerated, unusable at HEAD. `env-hash.json` therefore records a second value, `engine_hash`: the same record construction over the frozen-set paths under `crates/` only. Runs, bundles and verdicts carry and compare `engine_hash`; a run's own hypothesis, scenario and workload enter `run_id` through their own hashes. `env_hash` stays what the CON-7 gate checks, and a run still refuses to start when either value differs from the record. `cargo xtask env-hash` computes both and `--check` verifies both: the record's `engine_hash` must be the hash of its own frozen-crate entries, and a record without the field fails the gate with the command that regenerates it. Print mode still works on such a record, so the way out is always available.
