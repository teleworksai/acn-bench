# SPEC 140 — POC 16: the kit and regeneration

**Status:** Draft v0.1 (October 2026; written for T16). **Inherits:** SPEC 000, 010, 040, 050, 080, 085. **Prefix:** P16. **Hypothesis:** none (P16-1). **Crates:** `acn-cli` (`acn run --from-run-id`, finding inputs by hash), `xtask` (evidence pages, the quickstart check). Nothing in the frozen set changes (CON-7).
**Purpose:**
- regenerate any `sim` bundle from its `run_id` alone, on the same build, byte for byte (CON-5(c));
- define the kit a second group runs, and what a second machine must reproduce from it;
- give every hypothesis an evidence page (LOOP-30) that CI can keep current;
- give the README a quickstart that a test runs.

## 0. The question

Can a second group, with the kit and nothing else, regenerate the bundles behind a result and get the same bytes? POC 16 answers it with records, not a verdict: a regeneration either matches or names what differs.

## 1. Definitions

- **Reference manifest** — the `manifest.json` of a `sim` bundle, committed byte for byte as `kit/manifests/<run_id>.json` (P16-10).
- **Same build** — equal `build_hash` (CON-31): the same source tree, lock file, toolchain, configuration, target, profile, features and flags.
- **Regeneration** — re-running a bundle's inputs into a fresh directory and comparing the result with the original (P16-6).
- **Search roots** — the directories in which inputs are found by hash (P16-3).
- **Build-neutral form** — a bundle with what records its build taken out (P16-6): the manifest without `build` and without `files["resources.parquet"]`, and `resources.parquet` decoded with each row's `acn.build_hash` removed (TRC-19).

## 2. Regeneration

**P16-1** POC 16 MUST have no hypothesis file. Its evidence is regeneration records (P16-11, P16-12) and the gate that checks them (SPEC 095 §M1).

**P16-2** `acn run --from-run-id <run_id> [--runs-dir <dir>] [--across-builds]` MUST regenerate the `sim` bundle named by `run_id`. `<dir>` is resolved against the workspace root (CON-28).
- **The original manifest.** When `<runs>/<run_id>/` exists, the bundle MUST verify (TRC-23) and its manifest is the original; a bundle that does not verify is refused with `bundle_invalid`, never replaced by a reference manifest. Otherwise the original is `kit/manifests/<run_id>.json`.
- **Its checks.** The manifest MUST be in canonical form (TRC-23), and its `run_id` MUST recompute from its own fields (CON-29); otherwise `manifest_invalid`.
- **Only `sim`.** A `live` or `netem` manifest is refused with `not_reproducible_mode`: only `sim` claims byte identity (CON-5(c)).

**P16-3** The inputs MUST be found from the manifest's hashes alone, among the `*.toml` files under the search roots, directories named `target` excluded:
- **Workload.** The harness workload, or the generator's sheet (GEN-1), is the file whose BLAKE3 is `workload_hash`. The search roots are `workloads/`, `scenarios/`, `lab/`, `kit/inputs/` and `<runs>/ctl/scenarios/`.
- **Scenario.** It is the file with `scenario_hash` under the same roots, so that a trace-driven scenario's trace is found beside it as the scenario names it (CON-27(a), ADR-33). When the bundle exists, the text its `acn.scenario` span records (TRC-16, EMU-37) MUST be that file's bytes. A zero `scenario_hash` means no scenario (EMU-39).
- **Hypothesis.** With 32 zero bytes, the hypothesis is `none` and the seed is the manifest's. Otherwise it is the file with that hash under `hypotheses/`, `lab/hypotheses/` or `kit/inputs/` whose status, derived from where it lies as the harness derives it (frozen only under `hypotheses/`, HYP-3), is the manifest's `hyp_status`.
- **Missing inputs.** An input that is not found is refused with `input_missing`, naming the hash.
- **Duplicates.** Several files with one hash, and the status asked for, are the same bytes: the first in bytewise path order is used.

**P16-4** The run MUST be the one the manifest describes:
- **Kind.** The run is the generator's when `producers` names `acn-gen`, and the harness's when it names `acn-harness` and not `acn-gen`. Any other set is refused with `unknown_producer`.
- **Recorded fields.** The arm, `replicates`, every `vary.<name>` and every `opt.<name>` are taken from the manifest. An `opt.` absent from it is at its default (CON-29). For a harness run, `backend` and `model` are taken from it too. For a generator run they come from the sheet (GEN-1), and are checked against the manifest's.
- **Mock profiles.** These are the embedded ones (MLM-50), which the build covers.

The regenerated `run_id` MUST equal the original. Otherwise the regeneration fails with `run_id_differs`.

**P16-5** On another build (CON-31), the regeneration MUST refuse with `not_regenerable_with_this_build`, unless `--across-builds` is given. With the flag it runs anyway and reports a cross-build comparison (P16-6). It never claims identity: CON-31 claims byte identity only within one build. The flag reaches only builds of one engine: another `engine_hash` gives another `run_id` (CON-29), refused as P16-4 says.

**P16-6** The regeneration MUST write into a fresh directory, `<runs>/regen/<run_id>/<n>/`, with `n` the smallest positive decimal not yet used. The bundle lands at `<runs>/regen/<run_id>/<n>/<run_id>/`, never at `<runs>/<run_id>/` (CON-29). It is a scratch artifact and is never cited (as for LOOP-14). The comparison MUST be file by file:
- **On the same build,** every file of the bundle, `manifest.json` included, MUST be byte-identical to the original's, except under `logs/` (TRC-24). Without the original bundle, only the manifest can be compared, and it MUST be identical.
- **Across builds,** the bundles are compared in build-neutral form: every file but `manifest.json` and `resources.parquet` by hash, `resources.parquet` decoded, and the manifest as JSON. Without the original bundle, the regenerated files are compared with the hashes the reference manifest lists, `resources.parquet` excepted.

It MUST print one object (CON-8) with:
- `ok`;
- `run_id`;
- `dir`;
- `same_build`;
- `identical`, a bool;
- `differ`, the paths that differ, in bytewise order.

A refusal prints `ok: false`, a `code` (the names above) and an `error`, with the missing hash where there is one. On the same build, `ok` is `identical`. Across builds, `ok` reports that the regeneration completed, and `identical` is the evidence.

## 3. The kit

**P16-10** The kit MUST be this repository at a release tag. It ships `env-hash.json` and the frozen set, and is therefore a root (CON-28). It also MUST ship:
- `kit/manifests/`, the reference manifests of the runs it reproduces, committed in the tagged commit;
- `kit/inputs/`, any input that is not already under a search root;
- the README quickstart (P16-30).

A reference manifest is made by `cargo build -p acn-cli --locked`, in the dev profile (CON-31), on a clean checkout of the tag:
- nothing untracked under `crates/`, whose working tree `source_hash` covers;
- no `RUSTFLAGS`, and no user-level `rustflags` in the Cargo configuration.

Its `build` records the target. `build_hash` changes only with `crates/`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml` or `.cargo/config.toml`, and with the target, profile, features or flags (CON-31). So a commit that touches none of these, the reference manifests themselves included, keeps it.

`.gitattributes` MUST mark `kit/**`, `lab/**/*.toml` and `docs/runs/**/*.json` `-text`, so that these hashed and byte-compared files keep their bytes on every checkout (CON-27(a)).

**P16-11** A second-machine reproduction MUST be recorded in `docs/runs/<yyyy-mm-dd>-p16-<target>.md`. The record names:
- the tag;
- the target;
- every `BuildInfo` component and the `build_hash`, which on the same tag, target and conditions as P16-10 equals the one in the reference manifests;
- every `run_id` regenerated, with `identical`.

The machine checks out the tag, builds as P16-10 says, and runs `acn run --from-run-id` for each reference manifest of its target. Every result MUST be `identical`. This record is checked by the M1 gate (SPEC 095 §M1, T17), not by a test.

**P16-12** CI MUST, on each of its targets (CON-1):
- run one `sim` reference workload;
- regenerate it from its `run_id` on the same build, and require `identical`;
- publish the bundle's build-neutral form as an artifact: its files' hashes, its decoded resources and its manifest.

A later job, run whatever the matrix's outcome, MUST compare the three targets' artifacts and publish the comparison. A difference across targets is reported, never a failure (CON-31).

## 4. Evidence pages

**P16-20** For every loop whose results a gate or a page cites, these files MUST be committed byte for byte, each identical to its copy under `runs/` (LOOP-11, LOOP-12, LOOP-16):
- the loop's `report.json`, as `docs/runs/loop/<loop_id>/report.json`;
- every `twin.json` under it, as `docs/runs/loop/<loop_id>/twin/<verdict_id>/twin.json`;
- every `verdict.json` they name, the final L1 verdict and the L2 and L3 verdicts included, as `docs/runs/verdicts/<verdict_id>/verdict.json`.

The bundles stay under `runs/`. `acn evidence verify` is unchanged: it walks `runs/loop/` (LOOP-2) on a machine that holds the bundles, and the committed copies are what CI can read.

**P16-21** `cargo xtask docs-inventory` MUST render `docs/evidence/<hypothesis-id>.md` from the committed reports, twins and verdicts, and the gate documents, one page per hypothesis that has any (LOOP-30). The page shows:
- the current verdict at each layer, with its labels;
- whether it is citable (HYP-23);
- the divergence figures, from the twins (LOOP-12);
- the provider table, from the verdicts (HYP-24);
- the chain of `run_id`s and `verdict_id`s.

A page that shows an attribution quantity says that its network time is the emulated network's (ATR-42). `--check` fails when a page is stale, and when a committed report names a twin or a verdict that is not committed.

## 5. The quickstart

**P16-30** `README.md` MUST carry a quickstart: one fenced block whose info string is `sh quickstart`, holding the commands, one per line, that build the binary, run one `sim` bundle and regenerate it from its `run_id`.
- **Building.** The block's first line MUST be the kit's build command (P16-10).
- **Running.** Every other line starts with `acn`, and is run by a test with the binary the test was built with. A line is split into words by whitespace and run with no shell (CON-2): no pipes, globs or expansions.
- **`$RUN_ID`.** It stands for the `run_id` field of the JSON that the most recent line printed with one.
- **Passing.** Each line MUST exit 0, and the last MUST print an object whose `identical` is `true`. The test runs in a scratch directory under `target/` inside this checkout, as the control plane's suite does (ADR-39).

## 6. Acceptance tests

- `tests/accept/kit.rs` — P16-2 to P16-6, CON-5(c), CON-29. It runs:
  - a harness bundle and a generator bundle, each with and without a scenario, and a trace-driven scenario, regenerated `identical` from the bundle and from its manifest alone;
  - every refusal of P16-2 to P16-5: `bundle_invalid`, `manifest_invalid`, `not_reproducible_mode`, `input_missing`, `unknown_producer`, `run_id_differs` and `not_regenerable_with_this_build`;
  - the duplicates rule, and a hypothesis found only with the wrong status;
  - `--across-builds` on a manifest whose `build` differs, compared in build-neutral form;
  - the original directory untouched, and a second regeneration in the next `n`.
- `crates/acn-cli/tests/run_cli.rs` — P16-2, P16-6, CON-8: one JSON object, and exit 1 iff `ok` is false.
- `crates/xtask/tests/` — P16-10, P16-20, P16-21, P16-30:
  - an evidence page rendered from a committed report, twin and verdict;
  - the page stale under `--check`, and a missing committed twin or verdict failing it;
  - the ATR-42 statement for an attribution quantity;
  - the `.gitattributes` entries;
  - the quickstart block parsed and run.
- `.github/workflows/ci.yml` — P16-12: the per-target regeneration and the cross-target comparison artifact.

## 7. Open questions

1. **Cross-target identity.** P16-12's records will show whether bundles already agree across targets. If they do over a release, a later spec-change may claim it, and replace platform floats with `libm` where they don't (CON-31).
2. **Live reproduction.** A `live` bundle reproduces statistically, not byte for byte. Its reproduction is the twin's (CON-25, LOOP-12), not this spec's.
3. **What to publish of a loop.** SPEC 085 §8, question 3: all of the report, with provider raw responses redacted (TRC-42).
