# SPEC 000 — Constitution

**Status:** Draft v0.3 (September 2026; v0.3: CON-16 gains a solo-maintainer mode and says who merges; v0.2 added canonical encodings, the engine hash, run identity, seeds and the build hash as CON-27 to CON-31, the RNG pin in CON-5, normative wording for CON-6/9/10, and the scope file in CON-12). **Inherits:** none. **Owner:** Young He.
**Scope:** invariants that every other spec, crate, test and PR in acn-bench inherits. The key words MUST, MUST NOT, SHOULD, SHOULD NOT, MAY are as in RFC 2119. Requirement IDs `CON-n` are stable once published; retired IDs are never reused.

## 0. Project definition

acn-bench is an independent Rust project that (a) builds the experimental substrate described in the ACN Technical Report v1.2, Appendix E §E.2 — a deterministic network simulator/emulator, an agent-workload generator, an environment replayer and a control-and-evidence plane — and (b) runs the report's proof-of-concept catalogue (POC 1a–16) as frozen, falsifiable hypotheses with mandatory controls. It borrows the *method* of spec-driven development and testing from prior work and nothing else. ACN is an exploration of a new field: the POC catalogue is the current map, not the boundary, and this constitution deliberately separates an **exploration track** (`lab/`, §7) where ideas are cheap from a **substrate track** (`crates/`, `hypotheses/`) where results are defensible. Rigor is something an idea graduates into, not a precondition for trying it.

## 1. Platform and toolchain

**CON-1** The primary development platform is macOS arm64. All crates MUST build and pass `unit`, `integ` and `accept` tiers on macOS arm64 and on Linux x86_64/aarch64. Linux-only functionality MUST be isolated behind `#[cfg(target_os = "linux")]` and the cargo feature `netem`, and MUST NOT be required by any default build or test.

**CON-2** The implementation language is Rust, stable channel, pinned in `rust-toolchain.toml`, edition 2024. One Cargo workspace; crates under `crates/`. Python, notebooks, or any other language MUST NOT appear on the run path or the analysis path; shell is permitted only in `tools/*.sh`. Exceptions require an ADR (CON-15) naming the boundary and the reason.

**CON-3** The async runtime is tokio. No other executor MAY be introduced. Blocking work on the run path MUST go through `tokio::task::spawn_blocking`.

**CON-4** All trace and measurement data MUST be Apache Arrow in memory and Parquet on disk, under the schema of SPEC 010. JSON is permitted only for CLI results (CON-8), run manifests, hypothesis verdicts and control-plane messages (SPEC 070). CSV MUST NOT be produced or consumed on the run path.

## 2. Determinism and reproducibility

**CON-5** Determinism is a feature. (a) Every source of randomness MUST be an injected `ChaCha20Rng` seeded from the run seed, with per-component sub-streams derived by name as CON-30 specifies. The generator crate and every crate that turns its output into samples (`rand_chacha`, `rand_core`, `rand`, `rand_distr` where used) MUST be pinned exactly (`=x.y.z`) in the workspace manifest, and a golden-vector test MUST assert the first raw outputs of a named sub-stream, one ranged integer and one distribution sample; changing any of those crates or versions is a Class C change, because it silently invalidates every earlier run. (b′) Trace and span identifiers in `sim` mode MUST come from a seeded `IdGenerator` (SPEC 010, TRC-27). (b) Every source of time MUST be an injected `Clock`; `Instant::now()`, `SystemTime::now()`, `rand::thread_rng()` and equivalents MUST NOT be called outside `acn_emu::clock` and `acn_emu::rng`, enforced by clippy `disallowed_methods`. (c) In `sim` mode, the same (seed, scenario, workload, hypothesis, engine, mode, parameters, build) tuple MUST produce a byte-identical bundle, where *build* is the `build_hash` of CON-31 and the other members are the inputs of `run_id` (CON-29); nothing that can affect the bytes of a sim bundle MAY come from anywhere but the members of this tuple (a command-line option that does is an `opt.` parameter, CON-29). (d) In `live` mode the impairment schedule MUST be precomputed from the seed before traffic starts, the order in which cells, arms and replicates execute MUST be derived from the seed (sub-stream `run.order`, CON-30) and recorded in the manifest, so that a cold control followed by a warm treatment cannot be arranged, and outcomes are reported as distributions with replicate counts, never single runs. (e) Every bundle MUST carry a `run_id` derived from the seed, the scenario, workload, hypothesis and engine hashes, the mode and the run parameters, exactly as CON-29 specifies, and MUST be re-derivable from those inputs.

**CON-6** The substrate layout MUST be: `specs/`, `hypotheses/`, `scenarios/{synthetic,measured}/`, `crates/{acn-trace,acn-emu,acn-mockllm,acn-harness,acn-gen,acn-replay,acn-ctl,acn-hyp,acn-attrib,acn-cli,xtask}/`, `tests/accept/` (workspace package `acn-accept`), `tools/`, `docs/{decisions,gates,generated,lab}/`, `runs/` (gitignored). Adding a crate under `crates/` or changing the substrate layout requires a `spec-change` PR. `lab/` (§7) and other top-level directories MAY be added freely.

**CON-7** The frozen set is: `hypotheses/` (every file in it; a file there is *frozen* once `env-hash.json` records it, HYP-3), `scenarios/measured/`, `crates/acn-hyp/`, `crates/acn-attrib/src/core/`, `crates/acn-trace/src/schema/`. After the M0 gate, any change to the frozen set MUST be a human-merged PR labelled `env-change` carrying the updated output of `cargo xtask env-hash`, and MUST receive an adversarial review whose stated purpose is to break the integrity story. Automated agents and auto-research loops MUST NOT hold write access to the frozen set.

**CON-27** Canonical encodings. Every hash is plain BLAKE3 (`blake3::hash`, not keyed or `derive_key` mode) with a 32-byte digest, printed as lowercase hex. In every preimage of CON-27 to CON-31 and of SPEC 080, a digest is its raw 32 bytes, an integer is little-endian of its stated width (`seed` and `replicate_seed` are unsigned 64-bit), a *string* is its UTF-8 bytes preceded by its length as an unsigned 32-bit little-endian integer, and the preimage MUST begin with the stated ASCII context string, written bare (it is not length-prefixed) and terminated by one zero byte, so that no two derivations can collide. `env_hash` and `engine_hash` (CON-28) alone keep the un-prefixed record construction of ADR-4. (a) **File hashes.** `hypothesis_hash`, `scenario_hash` and `workload_hash` are each the `blake3` of one defining file's bytes as read from the working tree, never through git (a candidate may be uncommitted, a kit has no git, and a loop must see an edit the moment it is made, HYP-4). A defining file MUST name every other file it reads (a task corpus, a measured trace) together with that file's BLAKE3, as TRC-40 does, and the reader MUST verify each at load; one file hash therefore commits to the whole input, and inputs never use a tree hash. The repository MUST carry a `.gitattributes` that marks `hypotheses/**`, `lab/hypotheses/**` and `scenarios/**` `-text` (a spec that introduces another directory of hashed inputs adds it there), so that the working-tree bytes equal the committed blob on every checkout; `cargo xtask env-hash --check` in CI is what detects a divergence. A run with no hypothesis (fixtures, lab runs, LOOP-21 researcher sessions) uses 32 zero bytes, with hypothesis id `none` and status `candidate`. (b) **Tree hash.** Used only by `source_hash` (CON-31): `blake3("acn-bench/tree/v1\0" ‖ records)`, with the records written exactly as ADR-4 writes them — the path relative to the workspace root as bare bytes with `/` separators, one zero byte, the file hash as 64 lowercase hex characters, one `\n`, sorted bytewise by path; this is the one place a digest is not raw — and with ADR-4's walk rules: a symbolic link, a special file or a `.DS_Store` is an error, and a zero-length `.gitkeep` is skipped. (c) **Numbers written as text.** Wherever a number becomes a string (the values of CON-29, the keys of HYP-15, `manifest.json`, `verdict.json`): an integer is a decimal signed 64-bit value with no plus sign and no leading zeros; a float is an IEEE-754 double written exactly as the `ryu` crate formats it, which is the form `serde_json` emits (`150.0`, `0.05`, `1e21`, `1e-7`), and `ryu` MUST be pinned exactly as CON-5(a) pins the generator crates; a NaN or an infinity MUST be rejected where it is read; negative zero is written `0.0`; a bool is `true` or `false`. The value of a `range` parameter (SPEC 080) is always a float, whatever literal the TOML used (`5` is `5.0`), and of an `int_range` parameter always an integer. (d) **Known answers.** The PR that first implements a preimage of CON-27 to CON-31 or of SPEC 080 MUST add a known-answer vector for it (inputs and the expected digest, one of them with a float-valued parameter) to the citing test; from then on the vector is part of the encoding. A change to any encoding in CON-27 to CON-31 is a Class C change and takes a new context version (`/v2`).

**CON-28** Workspace root and the two environment hashes. The workspace root is the nearest ancestor of the current directory that holds `env-hash.json`. `env_hash` is the ADR-4 hash of the whole frozen set (CON-7); it is what the CON-7 gate and `cargo xtask env-hash --check` verify. `engine_hash` is the same construction restricted to the frozen-set paths under `crates/` (the verdict engine, the attribution core, the trace schema); `env-hash.json` MUST record both. Runs, bundles and verdicts are bound to `engine_hash` and never to `env_hash`: a run's hypothesis, scenario and workload already enter `run_id` through their own hashes, and if the whole set entered it, freezing one POC's hypothesis would change the `run_id` of every other POC's cells and make their bundles unusable (ADR-10). When a root is found, a run MUST recompute both hashes and MUST refuse to start if either differs from the record, or if `engine_hash` differs from the value its own binary embedded at compile time (CON-31), so that a consistent checkout cannot be run by a binary built from other frozen code. When no root is found, a run MUST refuse unless its hypothesis is `none` or a candidate, and `engine_hash` is then the embedded value. A published kit MUST ship `env-hash.json` and the frozen set, and is then a root.

**CON-29** Run identity. `run_id = blake3("acn-bench/run_id/v1\0" ‖ seed ‖ scenario_hash ‖ workload_hash ‖ hypothesis_hash ‖ engine_hash ‖ mode ‖ params_hash)`, where `mode` is one byte (0 `sim`, 1 `live`, 2 `netem`) and `params_hash = blake3("acn-bench/params/v1\0" ‖ pairs)`, `pairs` being, for each parameter in bytewise key order, the key as a string and then the value as a string, with no count. The keys are: `backend` (the `acn.backend` value of TRC-10), `model` (the model identifier requested from the backend; for `mockllm`, the mock profile name), `hyp_status` (`frozen` or `candidate`, HYP-3: the status is recorded in every bundle, so it has to be part of the identity), `arms` (sorted, comma-joined), `replicates` (decimal), one `vary.<name>` per `[varies]` parameter of the cell (SPEC 080), and one `opt.<name>` for each run option that can affect bundle bytes and differs from its default. The set of `opt.` names **and the default of each** MUST be listed in `acn_attributes.toml` and read from there, so that adding an option changes no existing `run_id` and changing a default moves `engine_hash`. Values are written as CON-27(c) specifies. In `live` and `netem` modes every option that can change what is sent to a provider or how the harness behaves (sampling parameters, token limits, endpoint host, retry and timeout policy, concurrency) MUST be an `opt.` parameter, and no environment variable other than credentials and logging MAY alter a run. A sim run, its live twin (CON-25), a mock run and a real-provider run of the same cell therefore have four different run IDs. A run MUST refuse to write into an existing `runs/<run_id>/` directory: in `live` mode the same `run_id` can yield different data, and a bundle is never silently replaced (TRC-23 gives each bundle a `bundle_digest`).

**CON-30** Seeds. A *derived seed* is the first 8 bytes, little-endian, of the stated hash with the most significant bit cleared, so that every seed fits a signed 64-bit integer (TOML, an OTel integer attribute, Arrow `Int64`). (a) `replicate_seed(i)` MUST be the derived seed of `blake3("acn-bench/replicate/v1\0" ‖ seed ‖ i)`, with `i` as an unsigned 32-bit little-endian integer. `acn.seed` (TRC-10) records the run seed and `acn.replicate` records `i`; `manifest.json` records the seed as a decimal string, because JSON readers lose integers above 2^53. (b) The seed of the component sub-stream `name` (ASCII) MUST be the 32 bytes `blake3("acn-bench/rng/v1\0" ‖ s ‖ name)` fed to `ChaCha20Rng::from_seed`, with `name` as a string and last, so that adding a component never shifts another component's stream. `s` is `replicate_seed(i)` for everything that belongs to one replicate (link models, mock timing, workload draws, the impairment schedule of CON-5(d), the trace and span ids of the replicate's sessions) and the run seed for everything that belongs to the run (the ids of the `acn.scenario` root span, the execution order `run.order` of CON-5(d), a loop's search `loop.search`, LOOP-14).

**CON-31** Build identity. `build_hash = blake3("acn-bench/build/v1\0" ‖ blake3(Cargo.lock) ‖ blake3(rust-toolchain.toml) ‖ blake3(.cargo/config.toml) ‖ source_hash ‖ target ‖ profile ‖ features ‖ rustflags)`, where `source_hash` is the tree hash of CON-27(b) over every file under `crates/`, except a `target` directory that is a direct child of a crate directory, plus the root `Cargo.toml`, read from the working tree without consulting git (a build from a kit tarball has no tracked set, and an un-added module is still compiled); `target` and `profile` are the build script's `TARGET` and `PROFILE`; `features` is the sorted, comma-joined list of `acn-cli`'s enabled features as spelled in its manifest, `default` excluded; and `rustflags` is `CARGO_ENCODED_RUSTFLAGS`, empty when unset; the last four as strings. It MUST be computed at compile time by a build script that reruns when anything under `crates/` changes, and embedded in the binary together with the `engine_hash` (CON-28) of the frozen code it compiled. Every manifest MUST carry `build_hash` and each of its components, so that a third party can check `source_hash` against a tagged tree. A binary whose bundles are cited MUST be built with `cargo build -p acn-cli --locked`, because building the whole workspace can unify features differently. `build_hash` is deliberately not an input of `run_id`, which identifies the experiment rather than the binary; a verdict refuses a bundle set that mixes builds within one mode (HYP-20). Byte-identity under CON-5(c) is claimed only between bundles whose `build_hash` is equal, and so only within one target triple; sim-path code SHOULD take transcendental functions from the `libm` crate rather than the platform's, so that identity across targets stays attainable, but it is not claimed.


## 3. Interfaces

**CON-8** Every CLI entry point (`acn <subcommand>`, `cargo xtask <task>`) MUST print exactly one JSON object to stdout, MUST write logs only to stderr via `tracing`, and MUST exit 0 if and only if the object contains `"ok": true`. The object MUST include `"run_id"` when a run was created or read, or `"run_ids"` when several were.

**CON-9** Pre-commit gates MUST be run in this order, chained with `&&`: `cargo fmt --all --check`; `cargo clippy --workspace --all-targets --all-features -- -D warnings`; `cargo test --workspace`; `cargo xtask trace-check`; `cargo xtask docs-inventory --check`; `cargo xtask env-hash --check`; `cargo deny check`. Class B changes add the affected acceptance suites; `netem` changes add the Linux ignored tier. Documentation-only changes MAY run only `fmt`, `docs-inventory` and `trace-check`.

**CON-10** Risk classes: **A** — `docs/`, `tests/`, `tools/`, `xtask`, `scenarios/synthetic/` (baseline gates). **B** — run-path crates (baseline gates plus affected acceptance suites). **C** — the frozen set (CON-7 procedure). A PR touching more than one class MUST be handled at the highest class it touches.

**CON-11** Commits follow Conventional Commits (`feat`, `fix`, `test`, `spec`, `docs`, `refactor`, `chore`, `ci`, `perf`) with a scope naming the crate or spec. One spec concern per PR. The PR description MUST list the requirement IDs satisfied. The repository squash-merges; the PR title is the mainline commit subject.

## 4. Tests as the spec's teeth

**CON-12** Test tiers are `unit`, `integ`, `accept`, `live`, `netem` as defined in CLAUDE.md. Every implemented MUST MUST be cited by at least one test function through a `/// Cites: <ID>[, <ID>…]` doc comment; which sections and IDs are implemented is declared in `trace-scope.toml`, and `cargo xtask trace-check` MUST fail when any requirement ID declared there has no citing test function, whatever its wording; MUST fail when a citation names an ID that does not exist; and MUST fail when a document or frozen hypothesis file refers to an ID that its written spec does not define (a reference to a spec that `specs/README.md` lists but that is not yet written is reported as a forward reference and does not fail). Acceptance tests for a POC MUST cite that POC's spec IDs and the hypothesis file it instantiates.

**CON-13** When a spec and a test disagree, the implementer MUST stop and open an issue titled `spec-conflict: <ids>`; neither the spec nor the test is changed in the same PR.

**CON-14** Agents MUST NOT edit `specs/` except in a PR labelled `spec-change` that states the rationale and the IDs added, changed or retired.

**CON-15** When a spec is ambiguous, the implementer MUST record the interpretation in `docs/decisions/ADR-<n>.md` (context, decision, consequences, IDs affected) and proceed. Work MUST NOT stall on ambiguity.

**CON-16** Review. (a) **Mode.** The project is in *solo-maintainer mode* while `.github/CODEOWNERS` on the PR's base branch has at least one entry and the owners named across all of its entries are one and the same `@user` handle, compared ASCII case-insensitively. Anything else — no file, no entries, an entry with no owner or with a token that is not an owner, an `@org/team`, an e-mail address, a second handle — is not solo-maintainer mode; and a PR that changes the owners CODEOWNERS names is handled under the stricter of its base and its head, so that a PR cannot remove the second owner to exempt itself. *The maintainer* is the human to whom that handle belongs; an agent session that uses the maintainer's credentials is not the maintainer. Write access SHOULD NOT be granted to a second person without adding them to CODEOWNERS in the same step. (b) **Solo-maintainer mode.** Independent review is not a merge condition: the maintainer MAY merge a PR once the CON-9 gates and every required CI check that ADR-6 names (`pr-check` included) are green on the PR's head commit. A review by a separate agent session SHOULD be requested for a Class C change (the adversarial prompt in `TASKS.md`) and for a Class B change the maintainer judges risky (the cross-review prompt), and a PR that changes a file already recorded in `env-hash.json` under `hypotheses/` or `scenarios/measured/` and merges without one MUST say so in its description. (c) **Otherwise** the person who merges MUST NOT do so until a person other than the PR's author has approved it as a GitHub review; an agent cross-review informs that approval and does not replace it. (d) **Who merges.** A PR is *human-merged* (CON-7, CON-22, LOOP-20) when the maintainer decided that merge for that PR. An agent MUST NOT merge a PR on its own initiative; it MAY run the merge only on the maintainer's instruction naming that PR. (e) In either mode, review findings are PR comments and a reviewer MUST NOT push to the branch under review. (f) This clause relaxes nothing else: the gates, the label rules (CON-7, CON-14), the human merge of CON-7 and CON-22 and, after the M0 gate, the adversarial review of CON-7 apply in both modes; with one maintainer that review is a separate agent session running the adversarial prompt in `TASKS.md`, linked from the PR. Solo-maintainer mode changes whether a second party must review, not what must pass.

## 5. Experimental integrity

**CON-17** A hypothesis file `<poc>.toml` (SPEC 080) states the hypothesis, the variables a loop may vary and their ranges, the measured quantities, the control, the falsifier as a machine-checkable predicate over the bundle, and the expected outcome. Hypotheses have a lifecycle: `candidate` files live in `lab/hypotheses/`, MAY be edited by anyone including automated loops, and produce verdicts labelled *exploratory*; a hypothesis becomes `frozen` by moving it to `hypotheses/` in a Class C PR, which MUST happen before the first run whose bundle is cited in a report, a paper or a working-group contribution. `acn hyp verdict` is the only path from a bundle to a pass / fail / inconclusive verdict, and it MUST label the verdict with the hypothesis status.

**CON-18** Every POC acceptance suite MUST run the control named in its hypothesis file under the same scenario as the treatment, and MUST report the treatment-minus-control effect with replicate count and confidence interval. A suite without its control is incomplete and MUST NOT close a gate.

**CON-19** `#![forbid(unsafe_code)]` in every crate. Library code MUST return `Result` and MUST NOT `unwrap`, `expect` or `panic!` except in tests and in `main` after error formatting; clippy `unwrap_used`, `expect_used` and `panic` lints are denied in library targets.

**CON-20** The substrate and every frozen-hypothesis result MUST run without `dora-rs`, `aisle`, Genesis, ROS or any robotics/dataflow framework: none of these MAY be a required dependency of a `crates/` member. Optional adapters (a partner's dora or ROS 2 stack, a specific radio testbed) MAY exist as feature-gated or `lab/` crates that attach at the control plane (SPEC 070) and the trace schema (SPEC 010). Ideas from other projects are welcome and are re-specified here when they graduate; source code is not copied.

**CON-21** Measured impairment traces under `scenarios/measured/` MUST carry a provenance file (collection date, device, location class, method, licence) and MUST NOT contain payload data or identifiers; only timing, size and link-state fields as defined in SPEC 020.

## 6. Milestone gates

**CON-22** Milestones M0–M4 are defined in SPEC 095. A gate closes only by a human-merged PR that adds `docs/gates/M<n>.md` recording the evidence the gate spec requires, including the run IDs of the bundles cited. No task marked as post-gate in `TASKS.md` MAY start before the gate closes.

**CON-25** Sim ↔ live twin. Any `sim` result that is cited, or that a loop uses to decide which cells are promoted to a higher layer (SPEC 085), MUST have a `live` run of the same scenario and seed schedule in the same bundle set, unless the hypothesis declares itself network-free (`twin_required = false`, LOOP-4); the per-quantity divergence MUST be computed by `acn hyp verdict` from the paired bundles, recorded in the verdict (HYP-22, HYP-28), and MUST be within the tolerance declared in the hypothesis file, otherwise the verdict is `inconclusive`. From M4 the same rule applies between `live` and `netem` on measured traces.

**CON-26** Mock backends are models, not results. Bundles whose inference backend is `acn-mockllm` MUST carry `backend = "mockllm"` and MUST NOT be cited as results; `acn hyp verdict` on such a bundle MUST label its output *mock-gated*. `acn-mockllm` MUST identify itself in every response, and a harness that sees that marker MUST record `backend = "mockllm"` whatever it was configured with; for every other backend the manifest MUST record the endpoint host, so that a real backend name over a mock or a cache is visible. Hypotheses that concern provider behaviour (caching, streaming, rate limiting) MUST be instantiated and reported per provider.

## 7. Exploration track

**CON-23** `lab/` is the exploration track. Anything under `lab/` is Rust (CON-2 still applies) but is exempt from CON-4 through CON-18, and from CON-27 to CON-31 unless it writes a bundle under `runs/`, except CON-8 for anything that becomes a CLI. The only gates for `lab/` are `cargo fmt` and `cargo clippy` on the lab crate itself, and a lab note in `docs/lab/<yyyy-mm-dd>-<slug>.md` stating the question, what was tried, what was learned, and whether it should graduate. Lab crates MAY depend on anything, including frameworks named in CON-20, and MAY break, be deleted, or contradict a spec. Nothing in `lab/` MAY be cited as a result.

**CON-24** Graduation: an idea moves from `lab/` to the substrate when someone wants to cite a number from it. Graduation means, in this order: a `spec-change` PR adding the spec and IDs; a candidate hypothesis file promoted to `hypotheses/`; tests citing the IDs; the control (CON-18). New POCs are expected to arrive this way; the catalogue in the ACN report is the current map, not a closed list, and `TASKS.md` carries an open exploration slot in every milestone.

## 8. Glossary

- **Bundle** — the directory produced by one run: manifest (JSON), traces (Parquet), logs. Verdicts read several bundles and live outside them (HYP-20).
- **Workload** — the defining file of what the generator or harness does in a run (generator parameters, tool set), which names any other file it reads, such as a task corpus, by BLAKE3. Its hash is the hash of that one file (CON-27a).
- **Scenario** — a TOML file naming link models, schedules and (optionally) a measured trace to replay.
- **`sim` / `live` / `netem`** — execution modes of `acn-emu`; see PLAN.md §2.
- **Control** — the non-agent or plain-RPC workload run under the same scenario as the treatment.
- **Falsifier** — a predicate over bundle statistics that, if true, refutes the hypothesis.
- **Candidate / frozen** — hypothesis lifecycle states (CON-17). Candidates are for exploring; frozen ones are for citing.
- **Lab note** — the only required output of an exploration (CON-23).
